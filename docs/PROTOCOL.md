# Dropper wire protocol — v1 (normative)

Both implementations (`pc/` on Windows, `android/` on Android) MUST follow this
document exactly. Byte-exact test vectors are in `docs/test-vectors.json`,
generated by `tools/gen_test_vectors.py` (an independent Python implementation).
Each side's unit tests check against those vectors.

The *why* behind these choices is in `SECURITY.md`. This file is the *what*.

---

## 1. Overview

| | |
|---|---|
| Roles | **PC** is the server. **Phone** is the client and always initiates connections. |
| Transport | TCP → 61-byte authenticated **preamble** → **TLS 1.3**, mutual certificate auth, both sides pin the peer's public key → length-prefixed **frames**. |
| Pairing | QR code shown on the PC (out-of-band channel) + 6-digit code the PC user confirms. |
| Discovery | Authenticated UDP request/response; the PC never answers unpaired devices. |
| Ports | TCP default **47823** (actual port travels in the QR / discovery response). UDP discovery is fixed at **47823**. |
| Scope | IPv4 LAN only. The PC listens only on physical LAN adapters on networks Windows marks Private or Domain (never Public), and accepts peers only from that adapter's subnet. The phone connects only over Wi-Fi/Ethernet to RFC 1918 addresses. |

## 2. Notation and primitives

- `||` is concatenation. All integers are **big-endian unsigned**.
- `SHA256`, `HMAC(key, msg)` = HMAC-SHA256.
- `HKDF(ikm, info)` = HKDF-SHA256 (RFC 5869), salt = 32 zero bytes, output length 32.
  Because L = 32 this is exactly: `HMAC(HMAC(0x00*32, ikm), info || 0x01)`.
- `b64u` = base64url **without padding** (RFC 4648 §5).
- Labels such as `"dropper/v1/gate"` are ASCII bytes, no terminator.
- Every MAC / proof comparison MUST be constant-time.
- Random values come from the platform CSPRNG (`RandomNumberGenerator` / `SecureRandom`).

## 3. Identities and fingerprints

Each device owns one **ECDSA P-256** key pair plus an X.509 certificate for it
(self-signed; the certificate is just a container for TLS, so its chain, names
and dates are never validated).

- **PC key:** Windows CNG, persisted, export policy *none*; created in the TPM
  ("Microsoft Platform Crypto Provider") when available, otherwise the software
  KSP (DPAPI-protected at rest).
- **Phone key:** Android Keystore (TEE), non-exportable. Purposes `SIGN|VERIFY`,
  digests `NONE, SHA-256, SHA-384, SHA-512`. **`DIGEST_NONE` is required.**
  Conscrypt signs the pre-hashed TLS transcript with `NONEwithECDSA`.

**Fingerprint:** `fp = SHA256(DER SubjectPublicKeyInfo)` (32 bytes).
Java: `SHA256(cert.publicKey.encoded)`. .NET: `SHA256(cert.PublicKey.ExportSubjectPublicKeyInfo())`.

**Display form:** uppercase hex of the first 16 bytes in 8 groups of 4, e.g.
`A0A1 A2A3 A4A5 A6A7 A8A9 AAAB ACAD AEAF`.

## 4. Secrets and key schedule

| Name | Definition |
|---|---|
| `pairing_secret` | 32 random bytes, made by the PC per pairing attempt, carried only in the QR code. Single use; expires 180 s after the QR is shown. |
| `device_secret` | 32 random bytes, made by the PC when the user **approves** a pairing. Sent once inside TLS (`PAIR_OK`). Stored encrypted at rest on both sides (DPAPI / Keystore AES-GCM). |
| `pair_gate_key` | `HKDF(pairing_secret, "dropper/v1/pair-gate")` |
| `pair_proof_key` | `HKDF(pairing_secret, "dropper/v1/pair-proof")` |
| `sas_key` | `HKDF(pairing_secret, "dropper/v1/sas")` |
| `gate_key` | `HKDF(device_secret, "dropper/v1/gate")` |
| `disc_key` | `HKDF(device_secret, "dropper/v1/discovery")` |
| `pc_gate_key` | `SHA256("dropper/v1/pc-pairing-gate")`. A public constant used only for the mode-3 preamble (§8.4). |

For PC-to-PC pairing (§8.4) there is no `pairing_secret`. The host PC still makes
the `device_secret`, and from then on the joining PC plays the phone's part in
every rule below: it connects, it sends the mode-1 preamble and it runs discovery.

## 5. Pairing QR code

```
dropper://pair?v=1&a=<ip:port>[,<ip:port>...]&k=<b64u(pc_fp)>&s=<b64u(pairing_secret)>&n=<percent-encoded PC name>
```

Phone MUST reject the QR unless **all** hold:
- `v` = `1`
- `k` and `s` each decode to exactly 32 bytes
- `a` holds 1–4 entries; each IP is a dotted-quad IPv4 in `10/8`, `172.16/12` or `192.168/16`; each port is 1–65535
- `n` decodes to ≤ 64 characters (display only; strip control characters)

Unknown parameters are ignored. The QR is the trust anchor: it gives the phone
the PC's exact public key, so no later step needs trust-on-first-use.

## 6. Connection establishment

### 6.1 Preamble (61 bytes, plaintext, sent by the client right after TCP connect)

"Client" means the phone, or a PC that joined another PC (§8.4).

| Offset | Size | Field |
|---|---|---|
| 0 | 4 | magic `"DRP1"` (`44 52 50 31`) |
| 4 | 1 | mode: `0x01` = session (paired device), `0x02` = QR pairing, `0x03` = PC-to-PC pairing |
| 5 | 8 | `ts`: sender wall clock, Unix epoch milliseconds |
| 13 | 16 | `nonce`: random |
| 29 | 32 | `mac = HMAC(key, bytes[0..29))`, where `key` = `gate_key` (mode 1), `pair_gate_key` (mode 2) or `pc_gate_key` (mode 3) |

The PC reads exactly 61 bytes (3 s timeout) and, **before any TLS byte is
processed**, checks that:
1. magic and mode are valid;
2. `|now − ts| ≤ 600 000 ms`;
3. `nonce` has not been seen in the last 20 minutes (replay cache);
4. for mode 1, `mac` matches the `gate_key` of some paired device (try each,
   constant-time). For mode 2, a pairing window is open and `mac` matches its
   `pair_gate_key`. For mode 3, a PC-pairing window is open, no attempt is in
   progress, and `mac` matches `pc_gate_key`. The mode-3 mac proves nothing
   because the key is public. It only keeps the greeting format uniform; §8.4
   carries the security.

On any failure the PC **closes the socket without sending a single byte**.
Failures are counted per source IP: a silent or truncated greeting, an invalid
preamble, and a failed TLS handshake all count. 10 failures within 60 s puts
that IP on a 5-minute ignore list. A successful mode-1 check tells the PC which
device to expect in TLS.

The timestamp check must not overflow on hostile values, so implement it as
`ts ≥ now − 600 000 && ts ≤ now + 600 000`, never as `|now − ts|`.

Connections that haven't completed the TLS handshake are "pre-auth". The PC
holds at most 16 of them, and at most 2 per source IP. When a new connection
would exceed either limit, the **oldest** pending one is dropped. That doesn't
count as a failure. This way an idle-connection flood only evicts its own
entries.

### 6.2 TLS

- TLS **1.3 only**. No session resumption, so every connection is a full
  handshake (PC: `AllowTlsResume = false`; phone: new `SSLContext` per connection).
- The PC is the TLS server and presents its identity certificate. It **requires**
  a client certificate.
- The phone is the TLS client and presents its Keystore key and certificate.
- **The phone checks** that the server leaf `fp` equals the pinned `pc_fp`.
  It ignores CA chain, hostname, validity dates and SNI.
- **The PC checks:**
  - mode 1: the client leaf `fp` equals the `fp` of the device whose `gate_key`
    matched, and that device is still paired. Re-checked after the handshake
    completes.
  - mode 2: accept any P-256 client certificate. The `PAIR_REQUEST` proof
    (§8.2) binds it to the QR secret.
  - mode 3: accept any P-256 client certificate. The joiner likewise accepts
    any server certificate. The code comparison in §8.4 binds both keys.
- A PC acting as client (a joiner) checks the host's leaf `fp` against the pin
  it stored, exactly as a phone does. It uses no revocation or AIA downloads.
- Handshake timeout: 10 s.

### 6.3 After the handshake

- **Mode 2 (pairing):** the phone sends `PAIR_REQUEST`. The PC answers
  `PAIR_OK` or `PAIR_FAIL`, then closes. After `PAIR_OK` the phone stores the
  pairing and reconnects in mode 1. No `HELLO` happens on a pairing connection.
- **Mode 3 (PC pairing):** the §8.4 exchange, then close. The joiner stores the
  pairing and reconnects in mode 1.
- **Mode 1 (session):** both sides send `HELLO` immediately (full duplex). Each
  waits ≤ 10 s for the peer's `HELLO`. After that, anything goes (§9). One live
  session per device: a new authenticated session from the same device replaces
  the old one, and the PC closes the old socket.

## 7. Framing (inside TLS)

```
frame := length:u32 || type:u8 || body
```

`length` counts `type` + `body`, so `length ≥ 1`. The maximum `length` is
`1 + 1 048 576`. A larger value, an unknown `type`, or invalid JSON in a JSON
frame is a **protocol error**: close the connection immediately.

JSON bodies are UTF-8 objects, ≤ 65 536 bytes. Unknown fields are ignored.
Required fields that are missing or have the wrong type are a protocol error.

| Type | Name | Body | Direction |
|---|---|---|---|
| `0x01` | HELLO | JSON | both |
| `0x02` | PING | empty | both |
| `0x03` | PONG | empty | both |
| `0x04` | BYE | JSON `{"reason": "unpaired" \| "shutdown"}` | both |
| `0x10` | OFFER | JSON | sender → receiver |
| `0x11` | ACCEPT | JSON `{"id"}` | receiver → sender |
| `0x12` | REJECT | JSON `{"id","error"}` | receiver → sender |
| `0x13` | DATA | raw bytes, 1 … 1 048 576 (senders use ≤ 262 144) | sender → receiver |
| `0x14` | END | exactly 32 bytes: SHA-256 of the whole content | sender → receiver |
| `0x15` | RESULT | JSON `{"id","ok"[,"error"]}` | receiver → sender |
| `0x16` | CANCEL | JSON `{"id"}` | sender → receiver |
| `0x20` | PAIR_REQUEST | JSON | phone → PC (mode 2 only) |
| `0x21` | PAIR_OK | JSON | PC → phone (mode 2), host → joiner (mode 3) |
| `0x22` | PAIR_FAIL | JSON | PC → phone (mode 2), host → joiner (mode 3) |
| `0x23` | SAS_HELLO | JSON `{"v","name"[,"model"]}` | joiner → host (mode 3 only) |
| `0x24` | SAS_COMMIT | JSON `{"commit"}` | host → joiner (mode 3 only) |
| `0x25` | SAS_NONCE | JSON `{"nonce"}` | joiner → host (mode 3 only) |
| `0x26` | SAS_REVEAL | JSON `{"nonce"}` | host → joiner (mode 3 only) |
| `0x27` | SAS_CONFIRM | JSON `{"ok": bool}` | joiner → host (mode 3 only) |

Writers MUST write each frame atomically. Use one write lock per connection so
that ACCEPT/RESULT/PONG frames interleave *between* the DATA frames of a
transfer going the other way, never inside them.

## 8. Messages

### 8.1 HELLO

PC → phone:
```json
{"v":1,"role":"pc","name":"DESKTOP-ABC","app":"1.0.0","addrs":["192.168.2.131:47823"]}
```
Phone → PC:
```json
{"v":1,"role":"phone","name":"Alex's S23 Ultra","model":"SM-S918B","app":"1.0.0"}
```
A PC that joined another PC (§8.4) is the client and sends the client HELLO with
`"role":"pc"` and `"model":"Windows PC"`. The host then accepts `role` ∈
`{"phone","pc"}` from the client. The client still requires `"role":"pc"` from the
server, and it uses `addrs` the same way the phone does.

`v` must be `1` and `role` must be the peer's role, otherwise it's a protocol error.
`name` ≤ 64 chars (display only, sanitized). The phone MAY replace its stored PC
address list with `addrs`, keeping only entries that pass the §5 address rules.

### 8.2 Pairing (mode 2)

`PAIR_REQUEST` (phone → PC):
```json
{"v":1,"name":"Alex's S23 Ultra","model":"SM-S918B","proof":"<b64u 32 bytes>"}
```
where `proof = HMAC(pair_proof_key, pc_fp || phone_fp)`, and `phone_fp` is the
fp of the certificate the phone presented in this TLS session.

PC procedure:
1. Recompute the proof from the TLS-presented client certificate and compare it
   constant-time. On mismatch: `PAIR_FAIL {"error":"bad_proof"}`, then close.
   That counts as a failed attempt; after 5 failed attempts the pairing window closes.
2. On a valid proof, **consume the pairing window**. Single use, whatever the
   user decides next.
3. Compute `SAS = (u32(HMAC(sas_key, pc_fp || phone_fp)[0..4]) mod 1 000 000)`,
   shown as 6 digits with leading zeros, formatted `"123 456"`.
4. Ask the user: *"<name> wants to pair. Only approve if your phone shows
   123 456."* Wait ≤ 120 s.
5. On approve: generate `device_secret`, store the device
   `{fp, cert DER, name, model, device_secret (encrypted), paired_at}`. An
   existing device with the same `name` is replaced. Then send:
   ```json
   {"v":1,"name":"DESKTOP-ABC","secret":"<b64u(device_secret)>"}
   ```
   On reject or timeout: `PAIR_FAIL {"v":1,"error":"rejected" | "timeout"}`. Then close.

`PAIR_FAIL.error` ∈ `rejected, timeout, expired, bad_proof, busy`.

The phone shows the same SAS (it can compute it locally) with the text
*"Confirm on your PC: 123 456"* and waits ≤ 150 s for `PAIR_OK` / `PAIR_FAIL`.

### 8.3 PING / PONG / BYE

- Either side may send `PING`; the other side must answer `PONG` promptly.
- The client (phone or joined PC) sends `PING` after 45 s with no frame sent. If no `PONG` arrives
  within 15 s, it reconnects.
- The PC closes a session that has received nothing for 120 s.
- `BYE {"reason":"unpaired"}` from the PC means the user removed this phone. The
  phone deletes its pairing and returns to the pairing screen. From the phone, it
  means the user unpaired on the phone (which also deletes its identity key). The
  PC removes that device's record. This is safe because only the paired phone can
  speak inside its authenticated session.
  `"shutdown"` means the peer is exiting; just reconnect later.

### 8.4 PC-to-PC pairing (mode 3)

Two PCs share no camera and no prior secret. They use numeric comparison with a
commitment, as Bluetooth Secure Simple Pairing does: each user reads a 6-digit
code on their own screen, and **both** must approve.

The **host** is the PC whose user clicked "Let another PC find this one". That
opens a PC-pairing window for 180 s. The window allows one attempt at a time. A
success closes it; 5 failed attempts also close it. The **joiner** finds hosts
with the §10.1 query and connects in mode 3.

All nonces are 32 random bytes, sent as base64url without padding. `fp_host` and
`fp_joiner` are the fingerprints of the certificates presented in this TLS session.

1. Joiner → `SAS_HELLO {"v":1,"name":"DESKTOP-JOIN","model":"Windows PC"}`.
   If another attempt is in progress or the window has closed, the host answers
   `PAIR_FAIL {"error":"busy"}` and closes.
2. Host picks `Na` and sends `SAS_COMMIT {"commit": b64u(C)}`, where
   `C = SHA256("dropper/v1/sas-commit" || Na || fp_host || fp_joiner)`.
3. Joiner picks `Nb` and sends `SAS_NONCE {"nonce": b64u(Nb)}`.
4. Host sends `SAS_REVEAL {"nonce": b64u(Na)}`.
5. The joiner recomputes `C` and compares it constant-time. On a mismatch it
   aborts. Something is in the middle.
6. Both compute
   `SAS = u32(HMAC(HKDF(Na || Nb, "dropper/v1/pc-sas"), fp_host || fp_joiner)[0..4]) mod 1 000 000`,
   shown as `"123 456"`. Both users are told to approve only if the other
   screen shows the same digits.
7. Joiner → `SAS_CONFIRM {"ok": true|false}` with its user's answer.
8. The host waits ≤ 120 s for **both** its own user's decision and the joiner's
   `SAS_CONFIRM`. It stops at the first "no". A hang-up or a malformed frame
   counts as "no".
   - Both yes: generate `device_secret`, store the joiner as a device of kind
     `pc`, and send `PAIR_OK {"v":1,"name":"DESKTOP-HOST","secret":"<b64u>"}`.
   - Otherwise: `PAIR_FAIL {"error":"rejected" | "timeout"}`.
9. On `PAIR_OK` the joiner stores the host as an **outbound** peer:
   `{fp_host, cert DER, name, device_secret (encrypted), last address}`. It then
   connects in mode 1 like a phone, using the same gate key, HELLO, ping cadence
   and discovery. Reconnect backoff: 2, 5, 15, 30, 60, 120 s. A network change
   resets it.

**Why the commitment matters.** A man in the middle runs one TLS session with
each PC, so each side's view has a different `fp` pair. To make both screens show
the same 6 digits, the attacker has to pick its own nonces so that two
independent HMAC outputs collide mod 10⁶. The host has committed to `Na` before
it sees `Nb`, and the joiner has sent `Nb` before it sees `Na`. The attacker
therefore can't search for a match. It gets one guess per attempt, a 10⁻⁶ chance,
and every attempt needs both humans to approve.

Pairing between two PCs is symmetric afterwards. Either side can send, and
`BYE {"reason":"unpaired"}` from either side removes the pairing on both.

## 9. Transfers

Each direction carries **at most one item in flight**. The sender sends the
next `OFFER` only after it receives `REJECT`, `RESULT` or, after it sent
`CANCEL`, nothing at all. Both directions may be busy at the same time.

```
sender                                receiver
  OFFER {id,kind,name,mime,size}  →
                                  ←   ACCEPT {id}   or   REJECT {id,error}
  DATA … DATA (Σ = size bytes)    →
  END <sha256>                    →
                                  ←   RESULT {id, ok[, error]}
```

`OFFER`:
```json
{"id":"<32 lowercase hex chars = 16 random bytes>","kind":"file"|"text","name":"photo.jpg","mime":"image/jpeg","size":123456}
```
- `kind = "text"`: the content is UTF-8 text; `name` may be `""`; `mime` is
  `"text/plain"`; `size` ≤ 4 194 304.
- `kind = "file"`: `name` ≤ 255 chars (untrusted; see §11); `mime` is a hint
  only; `size` ≤ 68 719 476 736 (64 GiB).
- A zero-byte item sends no DATA frames, just END = SHA-256 of the empty string.

**Receiver rules:**
- `OFFER` while another incoming item is pending is a protocol error.
- Answer `REJECT` instead of `ACCEPT` when there is too little free space
  (`"no_space"`), a limit is exceeded (`"too_large"`), the offer is malformed
  (`"invalid"`), the destination can't be created (`"io"`), or the `id` was
  already **completed** in the last 500 items (`"duplicate"`). The sender treats
  `"duplicate"` as *delivered*: it is a retry whose first RESULT was lost. Any
  other REJECT error means the item **failed**. Don't retry it automatically.
- Before `ACCEPT` is sent, DATA or END is a protocol error. So is a running
  total that exceeds `size`.
- On `END`: if the total equals `size` and SHA-256 matches, commit the item and
  send `RESULT {"ok":true}`. Otherwise discard it and send
  `RESULT {"ok":false,"error":"integrity"}`. On a local write failure, send
  `{"ok":false,"error":"io"}`.
- On `CANCEL` (valid only between ACCEPT and END): discard any partial data and
  send no reply.
- On disconnect mid-item: discard the partial data.

**Sender rules:**
- Wait ≤ 30 s for ACCEPT/REJECT, ≤ 60 s for RESULT after END, and stall at
  most 30 s between frames. A timeout means close the connection and treat it
  as a disconnect.
- On disconnect the item stays queued and is resent from byte 0 on the next
  session, with the **same id**. After 3 failed attempts it is marked failed and
  the user can retry it.
- Send `CANCEL` if the source becomes unreadable mid-stream.

## 10. Discovery (UDP 47823)

The phone uses discovery when its stored address is unreachable. It sends the
request to `255.255.255.255`, to the Wi-Fi subnet's directed broadcast address,
and to the last known PC IP.

**Request (60 bytes):**

| Offset | Size | Field |
|---|---|---|
| 0 | 4 | magic `"DRD1"` |
| 4 | 8 | `ts` (Unix ms) |
| 12 | 16 | `nonce` |
| 28 | 32 | `mac = HMAC(disc_key, bytes[0..28))` |

**Response (58 bytes, unicast to the request's source address and port):**

| Offset | Size | Field |
|---|---|---|
| 0 | 4 | magic `"DRD2"` |
| 4 | 4 | PC IPv4 address on the requester's subnet |
| 8 | 2 | TCP port |
| 10 | 16 | `nonce`, echoed from the request |
| 26 | 32 | `mac = HMAC(disc_key, bytes[0..26))` |

**PC behavior:**
- Reply only if all of these hold: the datagram arrived on a LAN adapter, the
  source IP lies in that adapter's subnet, `ts` is within ±600 s (checked without
  overflow, as in §6.1), the nonce is unseen, and the mac matches some paired
  device's `disc_key`.
- Otherwise stay **silent**.
- Send at most 20 responses per minute per source IP.
- The response is smaller than the request, so it cannot be used for amplification.

**Phone behavior:**
- Accept a response only if its mac verifies under the phone's `disc_key`, the
  nonce matches an outstanding request, and the IP is RFC 1918.
- Then connect to that IP and port, and save them as the new last-known address.

### 10.1 PC-pairing query (same UDP port)

A joiner looks for hosts with an open PC-pairing window (§8.4). Nothing here is
secret. A host's window is open for at most 180 s, and pairing still requires
the code comparison.

**Request (exactly 100 bytes, broadcast):**

| Offset | Size | Field |
|---|---|---|
| 0 | 4 | magic `"DRQ1"` |
| 4 | 16 | `nonce` |
| 20 | 80 | zero padding |

**Response (23 + n bytes, n ≤ 64, unicast to the request's source):**

| Offset | Size | Field |
|---|---|---|
| 0 | 4 | magic `"DRQ2"` |
| 4 | 16 | `nonce`, echoed |
| 20 | 2 | TCP port, big-endian |
| 22 | 1 | `n` = length of the name |
| 23 | n | PC name, UTF-8, at most 32 characters |

The host answers only while its PC-pairing window is open and not busy. It uses
the same LAN and subnet checks and the same per-IP rate limit as §10. Without an
open window, a PC is silent and can't be found. The padding keeps every response
smaller than the request, so the query can't amplify traffic. The joiner keeps
only responses that echo its nonce and come from a LAN subnet. It skips its own
address.

## 11. Receiver-side content rules

**Names.** Treat every name as hostile.
- Keep only the final path component; split on both `/` and `\`.
- Drop control characters and `< > : " / \ | ? *`.
- Trim trailing dots and spaces.
- Reject Windows device names (`CON PRN AUX NUL COM1-9 LPT1-9`, with or without
  an extension) by prefixing `_`.
- Cap the length at 150 chars, keeping the extension.
- An empty result becomes `file`.
- Never overwrite: if the name exists, use `name (1).ext`, `name (2).ext`, …

**PC files** go to `Downloads\Dropper\` (configurable). They are written to a
temp file in that folder, verified, then renamed. They are tagged with
Mark-of-the-Web (`Zone.Identifier` ADS, `ZoneId=3`) so SmartScreen and Office
Protected View treat them as downloaded. Never auto-open them.

**Phone files** go to `Download/Dropper/` via MediaStore (`IS_PENDING` while
writing). The MIME type is derived from the extension
(`MimeTypeMap`), falling back to `application/octet-stream`.

**Text** is never executed or auto-opened.
- A link is offered as **Open** only when the whole trimmed text is a single
  `http://` or `https://` URL.
- Auto-copying received text to the clipboard is a user setting (default on).

## 13. Test vectors

See `docs/test-vectors.json`. Inputs are fixed byte patterns. The file covers
every derived key, the proof, the SAS, both preamble modes, both discovery
packets, a HELLO frame, a PING frame, a QR URI and a fingerprint display string.
It also includes RFC 5869 test case 3, a sanity check of the HKDF implementation.
